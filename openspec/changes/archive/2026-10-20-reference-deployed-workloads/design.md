# Design

## Context

Today a project is "containerized" only when `project.tilt.k8s` makes the extension generate its manifest. The planner receives a set of project IDs and assumes one workload per project, named after the project (`tiltfile.rs`, `plan_with_images` and `plan`). The built-in template's `images` block emits `k8s_yaml(blob(...))` and `k8s_resource(...)` from `images.rs` (`Workload`, `K8sSettings`, `k8s_manifests`). See proposal.md for why this changes.

Verified against Tilt 0.37.8 while planning:
- Repeated `k8s_resource` / `dc_resource` calls for the same resource merge: labels and `resource_deps` are unioned, and other settings (e.g. `port_forwards`) from either call survive.
- A `k8s_resource` decoration evaluated before `k8s_yaml` (or `helm_resource`) defines the workload still applies, so call order doesn't matter for Kubernetes.
- `dc_resource` is different: called before `docker_compose()` loads the service, it fails with `no Docker Compose service found with name "<name>"` (exit 5). Compose decorations must come after the Compose file is loaded.
- Decorating a name that no deploy defines fails Tiltfile loading with `k8s_resource specified unknown resource "<name>"`.
- Resources created by the `helm_resource` extension accept `k8s_resource` decorations the same way: with `helm_resource('grafana', ..., labels=['sre'])`, a user `k8s_resource('grafana', trigger_mode=TRIGGER_MODE_MANUAL, links=[...])`, and the extension's `k8s_resource('grafana', labels=['grafana'], resource_deps=['db:serve'])`, the result has labels `grafana` and `sre`, the dependency, the manual trigger, and the link.
- Defining the same image ref twice (`docker_build` and `custom_build`, in either order) fails loading with exit code 5 and `Image for ref "<ref>" has already been defined`.
- Image refs with a registry prefix (`tilt.dev/api`) match a manifest's image verbatim in `custom_build`.

## Goals / Non-Goals

**Goals:**
- Containerization, selection, and project-graph links for any workload the user deploys, with any number of workloads per project.
- No deployment content generated by the extension.
- A guided migration for existing `project.tilt.k8s` users.

**Non-Goals:**
- Parsing or validating users' manifests, charts, or Compose files.
- `k8s_custom_deploy` or other deploy kinds beyond `k8s` and `compose`. (`helm_resource` releases are Kubernetes resources and are declared under `k8s`.)
- Issues #3 (toolchain `.prototools` interplay) and #4 (Tilt-adjacent tasks).

## Decisions

**Reference by declared name, and decorate.** The extension calls `k8s_resource(name, labels=[project], resource_deps=[...])` or `dc_resource(...)` for each declared workload, relying on Tilt's merge behavior. Alternatives:
- *Infer names by parsing YAML in the plugin*: kustomize and Helm render at Tiltfile load time, outside the plugin, so names aren't knowable from files.
- *Discover resources from Starlark*: Tilt exposes no API for listing defined resources.
- *Keep generating manifests and add escape hatches (issue #2)*: the schema-mirroring problem never ends, and label conventions (#5) still conflict.

**Kind-keyed declaration: `workloads: { k8s: [...], compose: [...] }`.** The kind is needed to choose `k8s_resource` or `dc_resource`, and the two functions aren't interchangeable. The alternative from issue #1, `workload: "api"`, can't express Compose or multiple kinds. A single list with per-entry kinds (`[{ name, kind }]`) is more verbose for the common case.

**Containerization comes from declared workloads, decoupled from images.** The planner's containerized input becomes a map from project ID to its workload names, instead of a set of project IDs. Each containerized project's service entry becomes its workload names, so upstream and downstream links fan out to every workload (spec: Workloads join the project graph). Images remain a separate opt-in (`project.tilt.image`), so a project can deploy a third-party image or a Helm chart without building anything.

**Containerization suppresses broad selections, not individually tagged build steps.** A containerized project's persistent tasks never run as local resources: the workload replaces them, even if a task carries the tag itself. Tasks selected through the project's tag or `includePersistent` are also suppressed. A non-persistent task that carries the tag itself (e.g. a schema export or codegen step) stays a local resource, with its non-persistent task dependencies, because the workload doesn't replace it. Suppressing every task (the first draft) would make such steps impossible to run from Tilt without moving them to another project.

**Workload labels are configurable with `workloadLabels: "project" | "none"`.** By default the extension labels each workload with its project ID, as it labels local resources. Workspaces whose Tiltfiles already label workloads by role (`server`, `worker`) see each workload twice in the Tilt UI's label groups, so `none` omits the label and adds only `resource_deps`. An enum rather than a boolean leaves room for other label schemes (e.g. by project tag or layer) without a breaking change.

**Compose-only projects restart their container, not the process.** `restart_process` (used for `serviceRestart: inputs`) overrides the image entrypoint, which Tilt rejects for Compose resources (`docker_build/custom_build.entrypoint not supported for Docker Compose resources`, found during end-to-end verification). When every workload a project declares is a Compose service, its image uses a plain `custom_build` with a `restart_container()` Live Update step, which re-runs the container's CMD (`moon run <project>:<startTask>`). Projects with any Kubernetes workload keep `restart_process`.

**Decorations go in a new `workloads` template block.** It follows `images` and replaces the `k8s_yaml` + `k8s_resource` emission there. The generated file includes project Tiltfiles before this block, so Compose services loaded there are defined before `dc_resource` runs. For Kubernetes, order doesn't matter, so the user's main Tiltfile can still include `Tiltfile.moon` before its own `k8s_yaml`. A main Tiltfile that loads Compose itself must call `docker_compose()` before `include("./Tiltfile.moon")`, which the README states. The project ID selection map includes the declared names, replacing the current single generated workload name.

**Removal is a hard error with migration guidance, not a silent ignore or a deprecation period.** Ignoring `project.tilt.k8s` would quietly stop deploying services. A deprecation period would keep the generator and its open issues (#2, #5) alive for a single known downstream user at 0.x. The error names `export-k8s` and `project.tilt.workloads`.

**`export-k8s` reuses the current generator once, to readable YAML.** The existing manifest-building code moves behind a CLI command that writes `<project>/k8s.yaml`, refuses to overwrite, and prints the `project.tilt.workloads` entry plus the Tiltfile lines (`k8s_yaml(...)`, and `k8s_resource(..., port_forwards=...)` when ports were set). It writes YAML rather than the JSON documents the template currently embeds, because the user will maintain the file by hand. `--output <path>` (relative to the workspace root) writes elsewhere, such as a shared `deploy/` directory, and the printed `k8s_yaml(...)` line uses the path relative to the project.

**The README warns about duplicate image builds when migrating.** Workspaces that already build an image in their own Tiltfile (`docker_build` or `custom_build`) and then set `project.tilt.image` for the same ref get Tilt's `Image for ref "<ref>" has already been defined` error. The README tells them to delete their own build when opting in, and that image names with a registry prefix are used verbatim as the `custom_build` ref.

## Risks / Trade-offs

- [A misnamed workload stops the whole Tiltfile from loading] → Tilt's error names the resource. The README documents that declared names must match what the project's Tiltfile deploys. The plugin can't pre-check names, because they come from Tiltfile evaluation.
- [Compose files loaded after the generated file's decorations fail loading] → Tilt's error names the service. Project Tiltfiles are always included first; the README tells main-Tiltfile users to call `docker_compose()` before the include.
- [Live Update restarts depend on the image entrypoint, which a user manifest's `command:` overrides] → With `serviceRestart: inputs`, `restart_process` wraps the image's entrypoint. Document that the manifest must not set `command:` for restarts to work, or that the app must reload itself.
- [Images only deploy if the user's manifest references the same image name] → Unchanged from today's build-only images. The README states the matching rule, and Tilt silently uses the published image on a mismatch.
- [A project opting into `project.tilt.image` while its Tiltfile still builds the same ref fails loading] → Tilt's error names the ref, and the README migration section says to remove the project's own `docker_build` / `custom_build`.
- [Breaking change for existing `project.tilt.k8s` users] → An explicit error, the `export-k8s` command, a README migration section, and a `feat(tilt)!` release (0.x minor bump).
- [Removing the readiness probe default] → `export-k8s` carries the probe into the exported manifest, so migrated projects keep it.

## Migration Plan

1. Release as `feat(tilt)!` through release-plz (0.x minor bump), with migration steps in the changelog and README.
2. Users run `moon ext tilt -- export-k8s <project>` for each project with `project.tilt.k8s`, then add the printed lines to the project's Tiltfile and `moon.yml`, and remove `project.tilt.k8s`.
3. Reply on issues #1, #2, and #5 linking the release. Close #2 and #5 as resolved by removal, and #1 as implemented.

Rollback: pin the previous release (`github://spaceribs/moon-plugins/tilt_extension@tilt_extension-v<previous>`).
